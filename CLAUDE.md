# Энериум

Мобильная idle-RPG с автобоем в тёмном фэнтези. Игрок — Странник; отряды до пяти героев спускаются в биомы под Эндалором. Цель — живой продукт: игровой сервер, клиент на Unity, админка и конструктор контента.

**Проект начат с чистого листа 26.09.2026** (ADR-0001). Всё прежнее лежит в архиве: репозиторий `eNeSpOo/Enerium` и папка `Enerium-archive` на диске. Там старые правила, они противоречат новым. **В архив не заглядывать** без прямого указания автора.

Исключение, которое автор уже назвал, — сырьё для арта и клиента. Брать его только по задаче и только арт, не правила:
- сцены, частицы и спрайты старого Unity-проекта из архива;
- библиотека арта второй версии игры 2022 года: `eNeSpOo/Enerium_New`, папка `Enerium_New`. В ней иконки предметов по ремёслам, иконки навыков, частицы и звуки. Опись — `art/README.md`.

**Где мы сейчас.** Сначала вся игра собирается в прототипе `design/ui/` (ADR-0026): все системы, данные, числа и арт. Прототип — эталон для переноса: схемы данных, ядро на C#, сервер, клиент Unity. Кода игры на C# пока нет. Что идёт прямо сейчас — `docs/STATE.md`.

## Инварианты

Нарушать нельзя. Основание — GDD, разделы 34 и 36.

- **Сервер решает, клиент показывает.** Расход, награды, исходы боёв и рецепты определяет только сервер.
- **Одно ядро расчётов** для сервера и клиента, без зависимости от Unity.
- **Только целые числа.** Время — целые миллисекунды, проценты и множители — фиксированная точка; никаких `float` и `double` в логике.
- **Вся случайность — от детерминированного генератора** с сидом, который выдал сервер. Порядок обращений к генератору — часть формата боя.
- **Числа баланса — в данных, не в коде.** Число в формуле — баг, даже если оно правильное. Исключения: 0, 1, индексы, размерности, алгоритмические константы.
- **Контент — данные, а не код.** Способности, враги, биомы, рецепты и награды собираются из примитивов; конструктор правит данные.
- **Рецепты и таблицы наград живут только на сервере.** Клиентская сборка не может до них дотянуться — это обеспечено типами, а не договорённостью.
- **Повтор запроса не повторяет расход и награду.** Каждая операция идемпотентна.
- **В Unity всё настраиваемое — объекты сцены.** Экраны, бой, параллакс, частицы и анимации — это сцены и префабы, которые правятся в инспекторе. Код связывает данные с ними, но не строит интерфейс сам (ADR-0002).
- **Честная модерация:**
  - критика игры — не нарушение;
  - за слова — только ограничение чата;
  - никаких коллективных наказаний;
  - бан аккаунта — только за читы и мошенничество, с доказательством из журналов сервера;
  - каждое действие модератора пишется в журнал.

  Админка устроена так, чтобы поступить иначе было нельзя.
- **Секреты — ни в репозиторий, ни в чат.** Ключи API и пароли — в переменных окружения или в локальных файлах из `.gitignore`.

## Как работаем

- **Начало сессии:** этот файл → `docs/ROADMAP.md` → `docs/STATE.md` → две последние записи `docs/progress/`. Задача про арт — ещё `docs/art-queue.md`.
- **Задача больше трёх файлов — сначала план,** затем ждать подтверждения автора.
- **Одно действующее правило.** Меняется правило — в том же изменении правится прежний текст:
  - раздел GDD переписывается под новое правило;
  - у прежнего ADR в статусе пишется «заменён ADR-NNNN» или «п. N отменён ADR-NNNN»;
  - в шапке нового ADR — поля «Заменяет» и «Уточняет»;
  - указатель пересобирается: `python tools/docs/adr_index.py`.

  Двух действующих текстов об одном быть не должно.
- **Вход агента в задачу:** этот файл → `docs/STATE.md` → `docs/decisions/README.md` → только те разделы GDD и ADR, что названы в задании. Координатор даёт агенту точный список чтения и список его файлов. Противоречие между текстами агент сам не разрешает — называет в отчёте.
- **Проверки:**
  - правка данных — пересборка по «Порядку сборки» в `tools/content-gen/README.md`;
  - перед коммитом — полный прогон `node tools/run-checks.js`;
  - экраны проверять ещё и глазами: кадры `node tools/ui-shots/shots.js` на двух экранах, 932 × 430 и 844 × 390. Пройденные проверки не значат, что экран выглядит как надо.
- **Конец сессии:**
  - запись в `docs/progress/ГГГГ-ММ-ДД-название.md`, 5–10 строк: что сделано, какие файлы, что осталось, подводные камни;
  - обновить `docs/STATE.md`, а если сдвинулось направление — и `docs/ROADMAP.md`;
  - важное решение — отдельный ADR и строка в указателе `docs/gdd/README.md`;
  - коммит. Отправку на GitHub делает автор кнопкой «Push origin» в GitHub Desktop.
- **Поиск по дереву — через подагента,** чтобы результаты не забивали контекст.
- **Ничего важного вне репозитория:** документы, решения, выгрузки других инструментов — сюда.
- **Отчёт автору — коротко:** состояние, а не пересказ работы.

## Соглашения по коду

Полный свод появится вместе с кодом отдельным ADR. Уже решено:
- язык C#: он общий для клиента Unity и сервера;
- `PascalCase` для типов и методов, `_camelCase` для приватных полей;
- формула — чистый метод со своим тестом и ссылкой на раздел GDD в комментарии: `// docs/gdd/05-боевая-система.md`.

В прототипе действуют те же инварианты: целые числа, числа — в данных, исход решает «сервер» прототипа, повтор операции ничего не повторяет. Подводный камень: `design/ui/index.html` и `tools/art-gen/ui-art.json` хранятся с концами строк CRLF. Правь их инструментом Edit или скриптом на node или python: `sed -i` в Git Bash снимает CRLF.
